# Research Hypotheses Registry

Every hypothesis must be falsifiable, tied to specific live metrics, and tested against a controlled baseline before any architectural claim is made.

| ID | Phase | Statement | Primary Metric(s) | Falsification / Refutation Criterion | Status |
| :--- | :---: | :--- | :--- | :--- | :---: |
| **H0 (Baseline Sanity)** | Phase 3 | Even *without* AI inference, an OpenFlow 1.3 `os-ken` reactive L2/L3 switch exhibits a measurable `Packet-In` saturation knee where p95/p99 handler latency, event-loop lag, and software flow-table occupancy rise nonlinearly as spoofed table-miss rate increases. | `packet_in_latency_p95_ms`, `packet_in_latency_p99_ms`, `event_loop_lag_p95_ms`, `controller_cpu_pct`, `benign_iperf_mbps`, `benign_new_flow_success_pct` | If `os-ken` handles all tested rates up to traffic-generator ceiling with flat latency (<2 ms p99) and <50% CPU, either generator rate is too low or switch datapath saturates before the controller. | `SUPPORTED (EXP-0002; WSL2 netdev)` |
| **H0b (Compute-Budget Knee)** | Phase 3/4 | Under core-pinned execution (`os-ken` isolated on Core 0) at a fixed sub-saturation attack rate (`250 pps` spoof -> `~500 Packet-In/s`, where base CPU is ~32%), injecting synchronous per-`Packet-In` CPU work (`[0, 0.25, 0.5, 1.0, 2.0, 4.0] ms`) saturates the single-threaded `eventlet` loop near the analytical ceiling (`~1.5 ms`), causing `event_loop_lag_p95_ms` to jump >10x and legitimate new-flow TCP setup success to collapse across `N=3` repeated seeds. | `controller_cpu_mean_pct`, `event_loop_lag_p95_ms`, `controller_packet_in_pps`, `benign_new_flow_success_pct`, `benign_new_flow_p95_ms` | Refuted if `os-ken` absorbs >=2.0 ms synchronous work per `Packet-In` at 500 `Packet-In`/s without CPU saturation or new-flow setup degradation. | `SUPPORTED (EXP-0005, N=3)` |
| **H1 (Bottleneck Attribution)** | Phase 4 | Inside a live Python SDN controller, synchronous multi-feature extraction (especially per-packet statistical features mimicking `CICFlowMeter`) and event-loop blocking contribute equal or greater tail-latency degradation than lightweight tree/linear inference alone. | Component breakdown (`extract_ms` vs `infer_ms` vs `flowmod_ms` vs `queue_wait_ms`), `event_loop_lag_p99_ms` | If model inference alone accounts for >80% of latency while feature extraction is negligible (<10%), feature-pruning hypotheses must be revised toward model/runtime optimization. | `REFUTED FOR PER-EVENT EXTRACTION / REFINED (EXP-0007: T3 extraction = 0.17 ms [4.7%], while batch=1 RF inference = 3.12 ms [85.2%]; even light LGBM/XGB batch=1 dispatch = 0.40-0.44 ms = 40x T1a extraction!)` |
| **H2 (Offline-to-Live Gap)** | Phase 4 | Models achieving nearly indistinguishable offline Macro F1 on leakage-free `InSDN`/`CIC-DDoS2019` splits exhibit large differences (>5x) in live p99 latency, controller CPU saturation point, and benign user throughput under flood conditions. | Offline Macro F1 & FPR vs. Live max sustainable `Packet-In`/s at p99 < 10 ms and benign QoS retention % | If heavy models impose negligible live overhead (<10% CPU delta, <1 ms p99 delta) under realistic loads, the bottleneck thesis is weakened. | `SUPPORTED (EXP-0006 + EXP-0007, N=3: T3+RF [99.98% offline F1] collapses live to 98.3% CPU, 29.5 ms loop lag, 16.7% new-TCP success & 0.03% live flood detection; T1a+LGBM stays 49.6% CPU & 100% new-TCP success at 250 pps)` |
| **H3a (Decoupled Async Windowed ML)** | Phase 5 | Moving windowed OpenFlow ML inference off `os-ken`'s `eventlet`/GIL loop into a separate core-pinned `multiprocessing` worker (`A2`) with targeted switch drop mitigation reduces controller CPU by `>50%`, cuts `event_loop_lag_p95_ms` by `>5x`, and restores legitimate new-TCP setup to `>=95%` under an `800 pps` spoofed flood compared to synchronous lightweight ML (`A1: Sync T1a+LGBM`). | `controller_cpu_mean_pct`, `event_loop_lag_p95_ms`, `benign_new_flow_success_pct`, `detection_to_mitigation_ms` | Refuted if `A2` fails to achieve statistically significant CPU/lag reduction or benign new-TCP survival improvement over `A1` across repeated seeds. | `UNTESTED` |
| **H3b (Stage-1 O(1) Gate + Flow-Table Guard)** | Phase 5 | Adding an O(1) Stage-1 port-rate gatekeeper + Selective Flow-Table Guard (`A3` vs. `A2`) eliminates Stage-2 ML invocations during normal traffic (`0` calls below gate threshold) AND reduces peak `s1` flow-table occupancy during attack onset by `>50%` with `0` `TABLE_FULL` refusals. | `s1_flow_table_occupancy_pct`, `table_full_errors`, `stage2_calls_during_benign`, `benign_new_flow_success_pct` | Refuted if `A3` does not materially reduce peak flow-table occupancy relative to `A2` or degrades benign traffic latency. | `UNTESTED` |
| **H3c (AI Necessity Under Benign Flash Crowd)** | Phase 5 | Under a legitimate high-rate bidirectional TCP flash crowd exceeding the Stage-1 gate threshold, a naive static rate limiter (`A4`) causes severe collateral blocking (`<50%` flash-crowd completion), whereas `A3` (Two-Stage Gate + Decoupled Windowed OpenFlow ML) distinguishes the benign flash crowd from spoofed floods and preserves `>=95%` legitimate completion. | `flash_crowd_success_pct`, `false_mitigations_on_benign_port` | Refuted if `A3` falsely mitigates the benign flash crowd (`<95%` completion) or performs no better than `A4`. | `UNTESTED` |
